## 零、一句话结论

**四类的代码依据和用户可执行动作全都已存在，缺的只是「呈现」。**

| 类 | 后端已有 | 前端消费 | 用户可做的动作 | 动作是否真实存在 |
| --- | --- | --- | --- | --- |
| ① 服务挂了 | `degraded` × 10 | **0 处** | 点「启动」 | ✅ `start-all` 1 处 |
| ② 功能降级（熔断） | `breakerOpen` / `retryInMs` | **0 处** | 等它恢复 / 重试 | ✅ `netRetry` 7 处 |
| ③ 无权限 | `EPERM` 3 处 / `unauthorized` | **0 处** | 插 USB 点「允许」 | ✅ 文案已有 |
| ④ 上游不可用 | `DHT 受限` 4 处 | 部分（仅 toast） | 直链下载 / 换源 | ✅ 文案已有 |

**判据**：不可用态必须带「用户能做什么」。四类动作全部存在，所以这不是凭空分类，是**已有能力没被呈现**。

## 一、四类的判定与呈现

### ① 服务挂了（进程死 / 端口拒连）

**判定**：`fetch` 抛 `TypeError`，耗时 **<50ms**（实测 0.0003s）
**区分要点**：被拒是**瞬间**失败；挂起是**等满超时**才失败——两者文案必须不同。

```
标题：音乐房没在运行
说明：服务进程已停止，页面拿不到数据。
动作：[启动]  ← 调 /api/start-all（已有）
```

**判据**：
```
1. 停掉某房后端 → 页面显示「没在运行」+「启动」按钮
2. 点「启动」→ 该房恢复后自动重载（不能要用户手动刷新）
3. 文案不得出现「网络错误」「检查网络」（用户会去重启路由器）
```

### ② 功能降级（熔断期）

**判定**：`/api/status` 返回 `degraded:true` + `breakerOpen:true` + `retryInMs`

```js
// hub.mjs:250-256 实测返回
{ running: false, status: 0, ms: null, degraded: true, breakerOpen: true, retryInMs: left }
```

```
标题：音乐房状态未知
说明：连续探测失败，暂停检查（约 45 秒后自动重试）。
动作：无需操作，会自动恢复
```

**这一条最关键**：现在是 `running:false` ⇒ 前端显示「已停止」，但**它可能活着，只是探测失败**。
`degraded:true` 就是后端明确告诉你「我不知道」。**把「不知道」显示成「已停止」是撒谎。**

**判据**：
```
1. 后端返回 degraded:true → 页面必须显示「状态未知」，不得显示「已停止」
2. retryInMs > 0 时显示倒计时或「约 N 秒后重试」
3. 熔断恢复后（degraded 消失）自动切回正常态，无需刷新
```

### ③ 无权限

**判定**：后端返回中文原因（`lib/photos.mjs:174/184`、`lib/cast.mjs:338`）

| 场景 | 后端原文 | 呈现 |
| --- | --- | --- |
| 相册被 TCC 拒 | `系统相册库受保护，未索引（读取被拒绝 EPERM）` | 原样显示 + 「打开系统设置」 |
| 投屏手机未授权 | `手机没授权调试：插 USB → 手机上点『允许 USB 调试』` | 原样显示（**这已是完整指引，不要改写**） |

**判据**：
```
1. 后端给中文原因 → 前端必须原样透出，不得替换成「加载失败」
2. 原因里已含操作步骤（插 USB / 点允许）→ 不得再包一层「重试」按钮（会误导成可自动恢复）
```

### ④ 上游能力不可用

**判定**：`lib/download.mjs:433` 的 DHT 受限文案、音乐版权限制

```
标题：磁力暂时连不上节点
说明：本机 UDP/DHT 受限，暂未连上外网节点；直链下载不受影响。
动作：[改用直链]  ← 明确告诉用户还有别的路
```

**判据**：
```
1. 文案必须说明「什么还能用」（直链下载不受影响），不能只说「失败」
2. 不得显示成「网络错误」——这是本机能力限制，不是网络问题
```

## 二、通用契约（四类共用）

### 2.1 每类必须有「动作」或明确的「无需操作」

| 类 | 动作 |
| --- | --- |
| ① 服务挂了 | 按钮「启动」 |
| ② 降级 | 文字「无需操作，会自动恢复」 |
| ③ 无权限 | 步骤指引（插 USB / 点允许）或按钮「打开系统设置」 |
| ④ 上游不可用 | 按钮「改用直链」或「换源」 |

**没有动作的不可用态 = 让用户干瞪眼 = 不合格。**

### 2.2 视觉：与「空」「出错」必须三者可分

现在 `.empty` 一个样式同时承担「暂无数据」和「出错了」，S1 已判 FAIL。加上不可用态后是**三者**：

| 态 | 视觉 | 类名 |
| --- | --- | --- |
| 空 | 虚线框 + 灰图标 + 「还没有…」 | `.empty` |
| 出错 | **红边** + 警示图标 + 「没读出来」+ 重试 | `.empty.error` |
| 不可用 | **琥珀边** + 状态图标 + 原因 + 动作按钮 | `.empty.unavailable` |

**判据（去色测试）**：灰度截图下三者仍能区分（边框虚实/图标形状/是否有按钮），不能只靠颜色。

### 2.3 位置：就地，不弹窗

不可用态出现在**原本该有内容的位置**，不弹 modal、不跳页。
理由：用户点进音乐房发现没运行，应该看到房内说明 + 启动按钮，而不是被弹窗挡住后不知道怎么回去。

## 三、失败长相（修复后仍可能出现的坏结果）

| 坏结果 | 为什么坏 | 判据 |
| --- | --- | --- |
| `degraded` 显示成「已停止」 | 撒谎，用户以为要去启动（其实活着） | 判据 ②-1 |
| 四类全显示成「加载失败」 | 用户不知道该做什么 | 每类文案必须不同 |
| 无权限给「重试」按钮 | 重试 100 次也不会获得权限 | ③-2 |
| 上游不可用显示「网络错误」 | 用户去重启路由器，白折腾 | ④-2 |
| 不可用态用 modal 弹出 | 挡住内容且不知如何返回 | 2.3 |
| 只有颜色区分三种态 | 色盲用户完全无法区分 | 2.2 去色测试 |

## 四、落地顺序（按今天真实发生频率）

| 顺序 | 事项 | 工作量 | 风险 |
| --- | --- | --- | --- |
| 1 | **消费 `degraded`** | 一行（后端已给 10 处，前端 0 处） | 极低 |
| 2 | 区分「被拒 / 挂起」 | 中（要测耗时 <50ms vs 等满超时） | 低 |
| 3 | `.empty.error` + `.empty.unavailable` 两个 CSS 变体 | 低（纯样式） | 极低 |
| 4 | 8 间房铺不可用态 | 大 | 中 |

**第 1 条单独就能让 8 间房的「状态未知」不再显示成「已停止」**——这是全组性价比最高的一行改动。

## 五、与 S1 的关系（避免重复改）

S1 判的是「出错 vs 空」不可分，S4 判的是「不可用」缺失。两者共用同一套 `.empty` 变体体系：

```
.empty                  空
.empty.error            出错（S1）
.empty.unavailable      不可用（S4）
```

**建议同一次改动做完**，否则 `.empty` 会被改两轮，必然漂移。
