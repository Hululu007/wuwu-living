## 一、先说结论（Rev1 已修，此处留档）

单参 `toast('...')` 走的是 `normalize(kind)` 的默认分支，**视觉上与成功提示完全相同**。
因此下面 3 处是**真缺陷**，不是风格问题：

| # | 位置 | 现在的代码 | 为什么是缺陷 |
|---|---|---|---|
| 1 | `五五客厅.html:1186` | `if (d && d.ok === false && d.message) toast(d.message);` | `ok===false` 才进来，这是**启动失败**，却用成功样式显示 |
| 2 | `五五客厅.html:1198` | `if (d && d.ok === false && d.message) toast(d.message);` | 同上，停止失败 |
| 3 | `相册.html:418` | `toast(d.ok ? '开始后台扫描' : '扫描没启动');` | 三元的 false 分支是失败，与 true 分支同一样式，用户看不出扫描没启动 |

**这三处必须改为 `tone:'err'`，其余 30 处属语义归位，不改也不会误导用户。**

## 二、tone 取值契约（迁移时按此填）

| tone | 何时用 | 行为 |
|---|---|---|
| `'good'` | 动作确认成功，且用户预期内 | 2.4s 自动消失 |
| `'err'` | **动作失败**，或用户需要知道「没做成」 | **常驻**，点击关闭，进 `Notify.history()` |
| `'info'` | 进行中 / 空操作 / 无内容可做 | 2.4s 自动消失，中性色 |

判据一句话：**用户看到这条之后，需要做的事不同吗？** 需要重试→`err`；只需知道→`info`；什么都不用做→`good`。

## 七、Rev2 收口：`'bad'` 的三个数字分歧已查清（重要，防误改）

三个管家报了 3 / 4 / 8 / 11 四个不同数字，根因是**同一个字符串在两处语义**：

```
投屏.html 共 11 处 'bad'，其中只有 9 处是 toast 的 tone：
  :649 :655 :883 :942 :973 :976 :1023 :1029 :1035   → toast tone（会被 normalize 认）
  :702   const dot = running ? 'live' : ready ? 'on' : 'bad';   → CSS 类名 .dot.bad
  :828   (a.ok ? 'ok' : 'bad')                                   → CSS 类名 .ar .r.bad
```

**按 `grep -c "'bad'"` 数会得到 11，按「toast 第二参」数只有 9。** 两者都不是错，但结论不同：
把 `:702` / `:828` 当 tone 去改，会**弄坏未连接手机的红点与操作结果的红字**。

**另一处必须知道的死代码：**
```
投屏.html:229   .toast.bad{border-color:rgba(222,66,23,.5);color:#f0b8b0}
书房.html:337   .toast.bad{border-color:rgba(217,132,132,.4);color:#f0c0bb}
```
`toast.js` 的 `normalize()` 把 `'bad'` 归一为 `'err'`，DOM 上写的是 `class="toast on err"`，
**永远不会出现 `bad` 这个类** ⇒ 这两条规则从未生效。且 `书房.html:337` 用的是旧 danger 色
`rgba(217,132,132)`（当前 danger 是 `#de4217` = 222,66,23），即使生效也不同源。
建议删除（属前端/上游文件，我只标注）。
