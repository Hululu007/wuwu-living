## 二、但迁移只解决"会不会被清"，没解决"会不会涨"

`out.log` / `err.log` 是固定文件名，**会无限增长**。launchd 的 plist 不支持 `$(date)`，
所以按日切分只能靠定时任务。

## 三、关键实现细节：必须 copytruncate，不能 mv

**为什么**：node 进程以 fd 持有该文件。`mv` 走后它仍写**旧 inode**，
新文件永远 0 字节 —— 这是日志切分的经典陷阱。

**我实测验证了截断是安全的**（不重启）：
```
截断前 out.log: 45 字节
: > out.log        → 0 字节
curl 触发请求      → 服务正常 200
进程 fd 仍指向 out.log，后续写入正常追加
```

## 四、切分脚本：`scripts/ops-rotate-8811.sh`

```bash
./scripts/ops-rotate-8811.sh --dry-run   # 只报告会做什么
./scripts/ops-rotate-8811.sh             # 执行
```

设计：
- `cat src >> dst` 再 `: > src`（copytruncate），**不 mv**
- 同日多次切分用 `>>` 追加，不覆盖
- 保留 14 天，自动清理更早的

## 五、三臂验收（退出码均不接管道取）

```
臂1 dry-run（空日志）      → EXIT=0  "无需切分（日志为空）"，未改动任何文件
臂2 真实切分               → EXIT=0
    "已归档 out.log (31 字节) → out-20261122.log"
    归档文件内容正确: "[test] rotation probe 16:23:49"
臂3 ★ 切分后服务仍写日志   → 切分前后 pid 均为 33810（未重启）
    fd 仍指向 out.log (size=0)
    kickstart 后新 out.log 写入 45 字节「聆听音乐网页版: ...」
    ⇒ inode 保住了，copytruncate 有效
```

**臂3 是这次最关键的一条**：只验证"文件被归档了"不够，
必须证明**切分之后服务还能继续往同一个文件写** —— 否则下次出问题就查不到日志了。

## 遗留
1. **切分时若 8811 正在写大量日志，`cat` 与 `:>` 之间有极短窗口可能丢几行**。
   本服务平时几乎不写 stdout（只在启动时打横幅），风险可忽略；若将来改成频繁写日志，
   应换成 `logrotate` 或让应用自己按日滚动。
2. 告警仍只到 macOS 通知中心（接外网要用户点头）。
