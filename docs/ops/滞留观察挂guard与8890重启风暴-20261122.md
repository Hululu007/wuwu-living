# 滞留观察挂进 guard + 一次 0/11 的归因（2026-11-22 19:10–19:16）

## 一、落地上一轮自己列的可改进：滞留观察挂进 guard

**问题**：`fixtures` 的滞留判据靠「跨次记住 CPU 累计时间」，但它只在人手动跑时才采样。
没人跑 = 没有样本 = 永远算不出「零增长 5 分钟」。**等于「只有被看时才存在」。**

**修法**：在 `ops-guard.sh` 里（launchd 每 5 分钟调一次）加一行采样：
```bash
bash "$DIR/scripts/ops-discipline.sh" fixtures >/dev/null 2>&1 || true
```
**只采样，不告警**——滞留不是故障（夹具等下一个用例时 CPU 本来就不涨），做成告警就是告警疲劳。

### 四臂
| 臂 | 条件 | 结果 |
|---|---|---|
| 正向 | guard 正常跑一次 | `EXIT=0`、`19:12:52 OK 8890=1 8811=1`，原有结论不变 |
| 采样发生 | 造活跃夹具后跑 guard | 状态文件自动写入 `25481 13 1795345983` |
| 超龄触发 | 首观测时刻调到 6 分钟前 | `观察 pid=26325 CPU 已 6 分钟零增长（累计 0:00.16）` + `PASS 1 个夹具全部合规` **EXIT=0** |
| 负向（关键） | 打 200 请求让 CPU 从 16→31 秒 | 首观测时刻**重置为 now**，观察不再触发 |

★ 第 3 臂与第 4 臂必须成对：只有「会报」证明不了「不该报时不报」。

## 二、一次 0/11 的归因（不是崩溃，是重启窗口）

验收时抓到 `十一入口 0/11`，全部 000。逐层查：

```
lsof :8890        → 有监听（pid=28952）
curl -v           → Recv failure: Connection reset by peer
last exit code    → 143（SIGTERM，不是崩溃）
runs              → 57 → 60（在涨）
```

连续 20 秒采样：
```
T0s  pid=29343  http=200  runs=59
T10s pid=       http=000  runs=60     ← 重启窗口
T15s pid=29530  http=200  runs=60
```

**结论：8890 在被反复重启（`runs` 48→60），我那次 0/11 正好落在重启窗口内。**
`restarts.log` 里 6 条 `RESTART(auto)` 都是 `检测者=ops-guard` —— guard 只是**事后记账**，
不是重启的原因（脚本里没有 kickstart/bootout/kill）。

**已排查并排除**：
- 实例锁冲突：`runtime/.instance.lock` 里 pid=29530 与当前一致，只有 1 个 hub 实例
- guard 自己重启：`grep kickstart|bootout|kill scripts/ops-guard.sh` 无命中
- 代码漂移触发：`hub.mjs` 18:19:37、`vod_recs.mjs` 19:12:24，晚于进程启动的只有后者（别人在改）

**稳定验证**：60 秒观察 `runs` 停在 60、pid 不变、请求 200 → 已稳定。
**当前**：十一入口 **11/11**、上游 7788/8811/8900 全 200。
