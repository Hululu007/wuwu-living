## 三、基线复核（并纠正我自己一次测量失真）

### 第一次测量：awk 取整导致假 0ms
```
for i in $(seq 20); do curl -w '%{time_total}'; done | sort -n \
  | awk '{a[NR]=$1} END{printf "p50=%.0fms", a[int(NR*0.5)]*1000}'
→ p50=0ms p90=0ms max=1ms     ← 全部 0ms，明显不合理
```
`%{time_total}` 是秒级小数（如 `0.000812`），`%.0f` 先取整成 0 再乘 1000 = 0。
**这是测量错误，不是接口变快了。** 改用 python 保留小数。

### 第二次测量（python，含重启窗口污染）
```
api/status        p50= 25.4ms  p90=562.7ms  max=741.6ms  超500ms=2/20
api/book/info     p50=  1.0ms  p90=  1.7ms  max=  3.8ms  超500ms=0/20
api/home/summary  p50= 32.9ms  p90= 75.1ms  max=169.3ms  超500ms=0/20
```
`api/status` 有 2/20 超 500ms，与总管报的「超 500ms 全部 0/20」不符。
**查明原因**：8890 的 pid 从 31353 变成 38430（16:22:04 重启），那 2 次超时落在重启窗口内。
**这不是接口退化，是又有人重启了服务。**

### 第三次测量（新进程 16:22:04 之后，排除重启窗口）
```
api/status        p50= 31.3ms  p90= 36.7ms  max= 81.9ms  超500ms=0/20
api/book/info     p50=  0.8ms  p90=  0.9ms  max=  1.0ms  超500ms=0/20
api/home/summary  p50= 33.4ms  p90= 39.8ms  max= 84.5ms  超500ms=0/20
```
**三条全部 `超500ms = 0/20`，与总管报的干净窗口基线一致。**
差异：`status p50 31ms` vs 总管 9ms、`summary p50 33ms` vs 9ms ——
数量级相同、都远低于验收线，差别来自采样时 load 7.86（总管测时 load 5.16）。
