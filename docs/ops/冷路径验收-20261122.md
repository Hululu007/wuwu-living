# 冷路径验收：`bookInfo` 从 2.249s → 14.9ms（2026-11-22 16:00）

## 总管定的判据（唯一能区分「改了代码」和「改了行为」）
> 重启后第一次请求会走冷路径。**如果还是 2.2 秒，说明 `hub.mjs` 那 344 行里没有真正修掉冷路径；
> 如果掉到毫秒级，才是真修好了。**

## 结果：掉到毫秒级

```
重启前 pid=3591  →  launchctl kickstart -k  →  重启后 pid=19131

FIRST  code=200  t=0.014917     ← 真冷（进程刚起、缓存空）
SECOND code=200  t=0.001396
```

**对比总管基线：冷 2.249s → 现在 14.9ms，约 150 倍。**

## 为什么这次是真的（三层证据，不是单点数字）

### 证据1：`groups` 聚合确实被砍掉了
```
curl /api/book/info → groups.len = 0,  groupTotal = 460
python3 lib/reader_query.py <db> info → {"sources":7538, ..., "groups":[], "groupTotal":460}
```
之前 `groups.len = 18`、且聚合要 json_extract 扫 7538 行 23MB。现在返回空数组、聚合不再跑。

### 证据2：`reader_query.py` 本身仍然要 225–325ms，但请求路径不等它
```
python3 lib/reader_query.py <db> info ×3 → 325ms / 232ms / 225ms
/api/book/info 冷打                  → 14.9ms
```
**这才是关键**：python 还是慢的（砍掉 groups 后从 2.2s 降到 0.3s，但仍是百毫秒级），
而接口只要 14.9ms ⇒ **请求路径没有同步等 python**，SWR 真的生效了。
如果只是"python 变快了"，接口不可能比 python 本身快 15 倍。

### 证据3：SWR 代码在 450–528 行
```
hub.mjs:450  * 结构照抄 lib/home.mjs 的 weatherForSummary()：旧值先用、后台补新、如实标 stale
hub.mjs:476  * 有值立刻给（过期就带 stale 并在后台补），没值立刻给 pending 占位并在后台去取
hub.mjs:484    return Object.assign({}, bookCache.data, { stale: true, ageMs: age })
```
返回体实测 `stale=false ageMs=87971` —— 说明缓存机制在按预期工作。
