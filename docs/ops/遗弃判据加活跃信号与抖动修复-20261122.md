# 遗弃判据：加活跃信号 + 修判据抖动（2026-11-22 18:33–18:45）

## 一、差点误杀一个正在跑的测试（最重要的修正）

`pid=76778 node hub.mjs` 端口 19079、`runtime=/tmp/ww-vod79`、**PPID=1**。
按「PPID=1 就是遗弃」应判红。但实测：

```
lsof -nP -a -p 76778 -iTCP
  TCP 127.0.0.1:19079 (LISTEN)
  TCP 127.0.0.1:19079->127.0.0.1:64318 (ESTABLISHED)
  TCP 127.0.0.1:64319->127.0.0.1:8900  (ESTABLISHED)   ← 正在跑 vod 冷路径测试
```
几分钟后它自己退了。

**根因**：父进程死 ≠ 进程没用。`nohup`/后台化 + shell 退出都会让 PPID=1，
真正在干活的实例仍在读写、仍有连接。

**修法**：PPID=1 只算「没人回收」，**必须再有「确实不动」的证据才判遗弃**：
```
有 ESTABLISHED 连接  或  runtime 近 2 分钟有写入  → 「在跑」，不判红
两者都无                                        → 「遗弃」，判红
```

### 对照臂（同一个 pid、同一个 PPID=1，只改一个变量）
| 臂 | 条件 | 判据输出 |
|---|---|---|
| 负向 | 造 19096，无连接无写入 | `遗弃 pid=86333 ... 无连接无写入` + FAIL 1 |
| 正向 | **同一 pid** 建 1 条 ESTABLISHED | `在跑 pid=86333 ... 连接 1 条` 不判红 |

**同一个 pid 在两次采样里被判成不同类别**，这就是这条判据有区分力的证明。

## 二、判据自己抖动（比判错更糟）

修完活跃信号后连跑 5 次，同一个 `pid=88526` 在「遗弃 / 在跑」之间反复跳：
```
第1: 遗弃[88526]
第2: 遗弃[] 在跑[88526]
第3: 遗弃[88526 89591]
```
**根因**：连接数是瞬时量，短连接场景下一次采样会漏掉。

**修法**：两次采样（间隔 1s），任一次见到活动就算在跑；两次都静默才判遗弃。

环境稳定后连跑 6 次，输出完全一致（遗弃[] 在跑[] 跳过=7）。

★ 但要如实说：那批 `/tmp/ww-stub.mjs` 是别人正在反复起停的测试，
**进程在生灭之间被采样，任何判据都会看到不同结果**——这不是判据缺陷。
判据能做的只是「同一时刻多采一次」，做不到「把别人的起停变静止」。

## 三、滞留观察（我上一轮列的可改进，本轮落地）

`pid=50832` 那种「父进程刚死、还没到明显遗弃」的早期残留，只靠 PPID 抓不到。
新增：跨次记住 pid 的 CPU 累计时间，**零增长 + 超龄（默认 5 分钟）** 时报「观察」。

**它只进 INFO，绝不计 FAIL**：夹具跑完一个用例等下一个时 CPU 本来就不增长，
判红会让正常跑测试的人被反复警告——与脚本头部「重启不是缺陷，否则告警疲劳」同一条理由。
