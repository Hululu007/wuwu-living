## 二、给 `/api/book/info` 定判据（后端管家请我给的）

**依据实测字段语义，不猜字段名：**
```
正常态：ok=true  dbOk=true  sources=7538  stale=false
失败态：ok=false dbOk=false sources=null  stale=true
pending：ok=true  dbOk=???   sources=null  stale=true
```

**四条互斥判据：**
| 编号 | 违反形态 | 为什么是缺陷 |
|---|---|---|
| V1 | `stale=false` 但 `sources=null` | stale 的含义是「旧」，数据为空不是「旧」而是「没有」；前端会把 null 画成「0 条书源」 |
| V2 | `stale=true` 但 `dbOk=true` 且 sources 有值 | 数据齐全可信却说不可信，自相矛盾 |
| V3 | `dbOk=false` 但 `stale=false` | 查询失败的数据被报成新鲜，等于把「没取到」当「取到了」 |
| V4 | 响应缺 `dbOk` 字段 | 消费方读到 `undefined`，与 `dbOk=false` 不等价 |

### 五形态实测（隔离靶子 19095）
```
good → EXIT=0  PASS  书房语义一致  STALE false SOURCES 7538 OK true DBOK true
v1   → EXIT=2  FAIL  stale=false 但 sources=null（把「没有」说成「旧」）

v4   → EXIT=2  FAIL  响应缺 dbOk 字段（消费方读到 undefined，与 false 不等价）
```

## 三、★ 实测发现的真缺陷：两个兜底返回缺 `dbOk`

对比三个 `return` 块的字段：
```
正常返回字段数=15
失败兜底字段数=18   缺: dbOk
pending 兜底字段数=17 缺: dbOk
```

**`hub.mjs` 的「失败兜底」与「pending 兜底」两个 return 都没有 `dbOk`**，而正常返回有。

为什么这是缺陷而不是小事：`undefined` 是「没说」，`false` 是「说了不可信」。
消费方写 `if (data.dbOk === false)` 会把「字段缺失」当成「数据可信」——
**缺失比假值更容易被静默忽略**。后端管家要补的是两处 `dbOk: false`。
