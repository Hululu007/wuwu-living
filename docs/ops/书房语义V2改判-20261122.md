# V2 判据改判：从 `stale` 改查 `untrusted`（2026-11-22 19:41–19:46）

## 一、我上一轮提的 V2 边界，被证实是真误报

上一轮我在「可改进」里写：V2 在 TTL 边界会误报，需后端确认「过期」与「不可信」是否该共用 `stale`。
后端管家的回答是**契约设计错**，不是判据写错，并把字段拆开了。

**误报机制（我的旧 V2）**：
```
正常取到 dbOk=true sources=7538，TTL=300s
age=301s（刚过 1 秒）→ stale=true  dbOk=true  sources=7538
这是正常 SWR 形态（旧值仍可信）
但旧 V2「stale=true 且 dbOk=true 且 sources>0」必然命中 → 永久假红
```

## 三、新契约
| 字段 | 含义 | 出现时机 |
|---|---|---|
| `stale` | 数据旧了、后台在刷，**旧值仍可信** | `age >= ttl` |
| `untrusted` | 数据来自**失败的查询**，本身不可信 | `dbOk===false` 或 pending |
| `dbOk` | 查询本身是否成功 | 三处 return 恒存在 |

两者可同时为 true（旧且不可信），但不再互相冒充。

## 四、判据改判（六条）
| 编号 | 违反形态 | 变化 |
|---|---|---|
| V1 | `stale=false` 但 `sources=null` | 不变 |
| **V2** | `untrusted=true` 却 `stale=false` | **改判：原来查 stale，现在查 untrusted** |
| V3 | `dbOk=false` 却 `untrusted` 未置位 | 跟着契约改 |
| V4 | 缺 `dbOk` 字段 | 不变 |
| **V5** | `untrusted=true` 但 `sources` 有值 | **新增**：不可信却给具体条数最危险 |
| **V6** | 缺 `untrusted` 字段 | **新增**：与 V4 同类 |

## 五、七形态实测（隔离靶子 19094）
| 形态 | 字段 | 结果 |
|---|---|---|
| `normal` | stale=false untrusted=false dbOk=true sources=7538 | **PASS** EXIT=0 |
| `ttlEdge` | stale=**true** untrusted=false dbOk=true sources=7538 | **PASS** EXIT=0 ← **旧 V2 会误报，新 V2 正确放过** |
| `failed` | stale=true untrusted=true dbOk=false sources=null | **PASS** EXIT=0（三字段自洽） |
| `fakeFresh` | stale=**false** untrusted=**true** sources=null | **FAIL** 两条：V1 + V2 |
| `untrustedWithNum` | untrusted=true sources=7538 | **FAIL** V5 |
| `noUntrusted` | 缺 untrusted | **FAIL** V3 + V6 |
| `noDbOk` | 缺 dbOk | **FAIL** V4 |

★ `ttlEdge` 与 `fakeFresh` 是这条判据的核心对照：
**同样的 `sources` 与 `stale` 组合，只差 `untrusted`，一个必须绿一个必须红。**
只有 `ttlEdge` 通过证明不了判据在工作——必须 `fakeFresh` 同时被抓到。
