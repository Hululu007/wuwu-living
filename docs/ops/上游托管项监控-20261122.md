# 上游托管项监控（补最后一个盲区，2026-11-22 17:07）

## 一、为什么加这条

上一轮发现 `/magnet/` 502 时，根因是 7788 死了——而 **7788 当时根本不在 launchd 里**，
所以它挂了不会自动拉起，房间就**永久 502**。

而 `ops-monitor` 只查客厅自己的托管项（`com.wuwu.wuwu-living`），**上游掉了完全看不见**。

**「房间 200」是当下能进；「上游被托管」是坏了能自己好 —— 两件事，不能互相替代。**

## 二、三个 web 类上游的托管现状（实测）

| 房间 | 端口 | launchd 标签 | 状态 |
|---|---|---|---|
| magnet 搜磁力 | 7788 | `com.wuwu.magnet-search` | ✅ 已托管 |
| music 听音乐 | 8811 | `com.wuwu.lingting.web` | ✅ 已托管 |
| vod 看视频 | 8900 | **无** | ❌ `nohup + /tmp/qingkan.pid` |

`book`（1122）是 `kind=app`，由 Reader 桌面 App 自己管，不属客厅启停范围，故不纳入。

**vod 的隐患**（`~/D盘/项目/请看/vod.sh`）：
```bash
PORT="$PORT" nohup "$NODE_BIN" server.mjs $ARGS > "$LOG" 2>&1 &
echo $! > "$PIDFILE"        # PIDFILE=/tmp/qingkan.pid
```
- 无 `KeepAlive` ⇒ 崩了不会自己起来
- pidfile 在 `/tmp` ⇒ 系统清理后连"它曾在这跑过"都查不到
- 日志 `/tmp/qingkan.log` 同样在易失目录

## 三、判据设计：不能一刀切判红

```
· 声明了 LABEL 的上游 → 查 launchctl print
    查不到 = WARN（房间当下可能仍可用，但坏了不会自动恢复）
· 没有 LABEL 的上游（nohup 型）→ 只记录，判 INFO，不判红
    「不用 launchd」是一种选择，不是缺陷；
    但它确实意味着挂了不会自动恢复，所以要**说出来**。
```

**为什么 WARN 不判 FAIL**：上游托管项丢失时房间**可能仍能用**（进程还在跑）。
判红会让「能用但不会自愈」和「已经坏了」混为一谈——这正是今天反复踩的坑
（把"不是缺陷"和"是缺陷"混在一个退出码里）。
