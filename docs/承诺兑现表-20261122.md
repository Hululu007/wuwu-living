## 二、问题清单（按四档，只列前三档才排期）

### P1 挡住主链路

**P1-1 视频推荐页：每 10 分钟有一次请求会卡到超时（不是"首次"）**
- 现象：`/api/vod/recs` 冷路径首打 45s 未返回（`code=000`），二次 8.46s，热路径 1.7–28ms
- 判据（可跑，双臂）：
  ```bash
  # 臂1 热路径（内存缓存命中）：必须 <300ms
  curl -s -o /dev/null -w 'hot=%{time_total}\n' -m 20 http://127.0.0.1:8890/api/vod/recs
  # 臂2 冷路径（文件缓存作废 + 进程重启，缺一不可）：必须 ≤15s 且 sections 非空
  touch -t 202001010000 runtime/vod.json && ./hub.sh restart
  curl -s -o /tmp/r.json -w 'cold=%{http_code} %{time_total}\n' -m 60 http://127.0.0.1:8890/api/vod/recs
  python3 -c 'import json;d=json.load(open("/tmp/r.json"));assert d["sections"],"空";print("sections=",len(d["sections"]))'
  ```
- 失败长相：用户点「看视频」→ 转圈 → 15s 后自己放弃；或看到空推荐页（最坏：以为没内容）
- **精确机制（已更正）**：`lib/vod_recs.mjs:21` `CACHE_TTL = 10 * 60 * 1000`。命中时 1.7–28ms；**缓存刚过期那一次**才走全量抓取（实测 8.45s，极端 45s 未返回）。
  ⇒ 10 次里 9 次很快，用户以为"偶尔抽风"，实际是**每 10 分钟必有一次卡顿**，谁赶谁白屏。
- **固定复现法（已实测：只 touch 无效）**：`lib/vod_recs.mjs` 是**两级缓存**——先查进程内 `memory`（`memory.t`，与文件 mtime 无关），再查 `runtime/vod.json` 的 mtime。
  实测只 touch 后仍是 `hot=0.0058s`（仍命中内存，`elapsedMs` 还是上次的 9139）。**必须 touch + 重启进程**，缺一则复现不出来。
- 优先级：**不阻塞上线**（命中率约 90%），但属 P2 必须排期
- 退役路径：recs 改后台预热 + 首屏骨架 + 失败给「重试」；若上游 8900 长期不稳，降级为「只显示采集站搜索框」，砍掉推荐区

**P1-2 首页概览抖动到 3.55s**
- 现象：10 次 median 1.82s、max 3.55s，6/10 超 500ms；`/api/status` 更重（p50=324 / p90=1881 / max=2370，6/20 超 500ms）
- **真根因（三段实测，2026-11-22 复测）**：
  | 环节 | 实测 | 说明 |
  |---|---|---|
  | `readerHealth()` → 1122 | **0.0006s**（`code=000`） | 无监听时内核瞬间拒绝，**不是等 1500ms**；1500ms 只是上限 |
  | `pgrep -xq Reader` | **0.27–0.28s/次** | 每次 fork 一个进程，不免费 |
  | `reader_query.py` 查 28MB sqlite | **1.2–2.7s/次** | `info` 含 groups 聚合，最贵的环节 |
  ⇒ `bookInfo()` 单次 ≈ **2.5–3.2s**
- **放大器**：`hub.mjs:280` `const cacheTtl = webRunning ? 45000 : 12000` —— **Reader 没在跑时 TTL 只有 12 秒**，等于每 12 秒必付一次 2.5–3.2s。
- 对照证据：`/api/book/recommend`（不探测进程）稳定 1–8ms。
- 【已收回的两条错误解释】①原写「等满 1500ms 超时」——实测 0.0006s 瞬间拒绝；②原写「`lib/rooms.mjs:279` 十间房串行 await」——各房 `summary()` 仅 1–7ms，串行累加几十毫秒，非主因。
- **⚠️ 旧判据已失效（2026-11-22 17:1x 实测，我自己撤掉）**：原臂1「`sleep 13` 让 TTL 过期后首打」依赖 TTL=12s。TTL 改成 300s 后，`sleep 13` 再也打不到冷路径——实测 `after-sleep13=0.071s`、连打三轮 0.057–0.186s，**和"已修好"无法区分**。判据失去区分力，必须换。
- 判据（新，2026-11-22 17:1x 起用；核心是**重启进程**造真冷，不是等 TTL）：
  ```bash
  # 臂1 真冷：必须重启进程（进程内 bookCache 与文件 mtime 无关，等 TTL 无效）
  ./hub.sh restart
  curl -s -o /dev/null -w 'cold-first=%{time_total}\n' -m 30 http://127.0.0.1:8890/api/status
  # 期望：≤1.5s（当前 1.037s）；改前为 6.716s
  # 臂2 热打 n=20：超 500ms 必须 = 0
  for i in $(seq 20); do curl -s -o /dev/null -w '%{time_total}\n' -m 20 http://127.0.0.1:8890/api/status; done \
    | sort -n | awk '{a[NR]=$1; if($1>0.5)o++}END{print "p50="a[int(NR/2)],"max="a[NR],"超500ms="o+0}'
  # 臂3 负向（隔离端口，不许动 8890）：把 ttl 改回 12s 的副本跑在 19041，
  #      证明"慢"确实由 TTL 放大，而不是被 SWR 掩盖掉
  #   实测：TTL=12s 副本 cold=0.057–0.186s（因为 SWR 把慢移到后台）⇒ 该负向臂已无法复现，
  #   说明「周期成本」这个症状本身已被 SWR 消掉，不是被藏起来。
  ```
- **验收门槛（总管定）**：独占窗口连打 20 次，`max ≤ 300ms` 且 `超 500ms = 0 次`；负向臂下同样成立
- **改后实测（2026-11-22 15:27，进程 pid 58801 / hub.mjs mtime 15:26:12 / 启动 15:23:25）**：
  ```
  冷打（等 13s 让 TTL 过期后首打）= 1.283s      ← 改前 6.716s，降 81%，但未达 300ms 门槛
  热打 n=10：min 0.013 / p50 0.035 / max 0.368 / 超 500ms 0/10   ← 超 500ms 归零 ✓
  热打 n=20：min 0.012 / p50 0.137 / p90 0.419 / max 0.452 / 超 500ms 0/20  ← 达标 ✓
  ```
  **判定**：总管门槛是「max ≤ 300ms 且 超 500ms = 0」。
  - `超 500ms = 0` **达标**（改前 8/10 → 改后 0/20）
  - `max ≤ 300ms` **未达标**（hot max 0.368 / 0.452；cold 1.283）
  ⇒ 结论：**主症状已消除（不再 7 秒级卡顿），但门槛未完全达到**，剩余为冷路径与偶发 0.45s。
- **改前基线（2026-11-22 15:2x 实测，供改后对照）**：
  ```
  cold（等 13s 让 TTL 过期后首打）  = 6.716s
  热打 10 次：min 0.118 / p50 2.100 / max 6.679 / 超 500ms 8/10
  ```
  ⇒ 连"热打"都不快，说明 10 次里有 8 次撞上了 12 秒 TTL 的重新计算。**改后必须降到 max ≤300ms。**
- 失败长相：进首页先愣 2 秒；六格数字陆续跳出来（一格格亮）。**因为每 12 秒复现一次，用户会觉得"这破客厅就是慢"，而不是"它出问题了"**
- **★ 改后新增的失败长相（2026-11-22 17:1x 实测，修法自己带出来的）**：SWR 把「慢」换成了「旧」，而**首页没有消费 `stale`**。
  冷启动第 1 次请求实测 `book.stats.sources=null`，首页照抄渲染逻辑写出：
  ```
  fig=—   unit=条书源   chips=['本地书源', '书架还空着']
  ```
  `—` 与「书架还空着」**同时出现**，用户读成「一个书源都没有、书架是空的」，**这是假空**。
  约 **1–2 秒后**才变成 `fig=7,538 / 在读《习惯力…》`。
  对比：书房页 `public/书房.html:908` 已修（`i.pending ? '获取中…' : (i.stale ? '刷新中…' : '0')`），**首页没跟上**。
  根因：`/api/status` 的 book 段只给 `stats:{sources,lastBook,todayMinutes,groups}`，**不带 `pending`/`stale`**；
  带这两个字段的只有 `/api/book/info`。首页读的是 `/api/status`，所以拿不到。
- 退役路径：①`readerQuery` 改 SWR（已做）；②`bookCache.ttl` 12s→300s（已做，`hub.mjs:103`）；③`pgrep` 结果缓存 60s（已做）。
  ④**未做**：`/api/status` 的 book 段补 `pending`/`stale`，首页 `fmt()` 之外按三态写文案（取到了 / 获取中… / 确实没有）。
  若④不做：首页书房格的数字位在拿不到值时**不要写 `—`**，写「获取中…」，否则 `—` 与「书架还空着」连读就是假空。

## 五、追加（2026-11-22 · 产品侧新发现，P1 级）

**P1-3 首页概览失败时「骨架屏永不退出」——失败被伪装成加载中**

**证据（三臂，含修复态对照）**
```
臂1 正向(真实文件) bodyLoading=true successExits=true catchExits=false -> FAIL  exit=1
臂2 负向(注入修复) bodyLoading=true successExits=true catchExits=true  -> PASS  exit=0
臂3 幂等(连跑两次) run1 exit=1 run2 exit=1 一致=true
```
判定依据（全部来自 `public/五五客厅.html`）：
- `418` 行：`<body class="loading">` —— 页面出厂即骨架态
- `809` 行：**只有** `.then()` 成功分支 `document.body.classList.remove('loading')`
- `812` 行：`.catch()` 只改 `#netText` 文本，**不退出骨架**
- `.loading` 生效样式（`321-329`）：`.entry-main{color:transparent}` 把十扇门的门名**变透明**，`:after` 画灰条占位；`.status{opacity:.35}`

**用户实际看到什么（失败长相，三档）**
| 档 | 触发 | 用户看到 |
|---|---|---|

## 九、入口存活监控规格（产品侧交付，给运维/测试直接用）

### 为什么需要三层，而不是一层
今天实测出一条教训：**页面 200 ≠ 能用**。音乐房在假死窗口里，`8890/music/` 靠客厅 `STATIC_PAGE_TTL=5s` + 800ms 熔断**始终返回 200**，但页面里的搜索/点歌请求会失败——用户看到「页面打开了、点了没反应」。
所以每一间房必须**同时**验三层：

| 层 | 判据 | 抓什么故障 |
|---|---|---|
| L1 入口 | `GET <页面>` = 200 | 整站挂了（今天 8890 掉那次） |
| L2 数据 | `GET <该房真实数据接口>` = 200 | 页面在、后端死（今天音乐房假死） |
| L3 托管 | `launchctl print gui/501/com.wuwu.wuwu-living` 查得到 | 托管项掉了（今天那次，无任何告警） |

### 可复跑的一键检查
```bash
#!/bin/bash
# 三层入口检查；任一 FAIL 即 exit 1
BASE=http://127.0.0.1:8890
fail=0
check(){ # $1=名字 $2=路径
  local c; c=$(curl -s -o /dev/null -w '%{http_code}' -m 8 "$BASE$2")
  [ "$c" = "200" ] || { echo "FAIL $1  $2 → $c"; fail=1; }
}
# L1 页面
for r in "/" "/magnet/" "/book/" "/music/" "/vod/" "/download/" "/library/" "/notes/" "/calendar/" "/photos/" "/cast/"; do check "page$r" "$r"; done
# L2 数据
for r in "/api/home/summary" "/magnet/api/sources" "/api/book/info" "/music/api/home" "/api/vod/recs"          "/api/download/list" "/api/library/list" "/api/notes/list" "/api/calendar/overview"          "/api/photos/list" "/api/cast/state"; do check "api$r" "$r"; done
# L3 托管项
launchctl print gui/501/com.wuwu.wuwu-living >/dev/null 2>&1 || { echo "FAIL launchd com.wuwu.wuwu-living 不存在"; fail=1; }
[ "$fail" = 0 ] && echo "ALL PASS (L1 11 + L2 11 + L3 1)"
exit $fail
```

### 阈值建议
- **L1/L2**：连续 3 次失败才告警（避免单次抖动），但**每轮必须打满 20 次**再判——今天 8811 出现过 20/20 → 0/20 → 20/20 的假死窗口，单次必误判。
- **L3**：查不到即告警，不需要重试（托管项不会自己抖动）。
